# Railroad Tycoon Spiritual Successor — V1 Specification

Status: Initial implementation baseline
Game mode: Open-ended sandbox
Rendering: Real-time lightweight 3D with orthographic camera
Primary runtime: Godot 4.7.2 Standard
Asset authoring/compiler: Blender 4.5 LTS
Primary runtime language: GDScript
Target: Desktop first

---

# 1. Product vision

Build an open-source railroad management game inspired by the gameplay clarity and economic loop of classic Railroad Tycoon games.

The game should feel like an interactive miniature railway diorama.

The visual identity combines:

* isometric presentation
* voxel-inspired geometry
* stylized low-poly modeling
* strong silhouettes
* restrained color palette
* miniature/diorama proportions
* smooth mechanical animations
* close inspection of trains and industries

The game must remain extremely lightweight despite supporting:

* continuous zoom
* very close zoom
* 360° horizontal camera rotation
* animated trains
* animated industries
* large maps
* thousands of repeated scenery objects

The V1 is a sandbox.

There is deliberately:

* no victory condition
* no campaign
* no score
* no competing company
* no stock market
* no multiplayer

The primary success criterion is:

> Building a railway, purchasing a train, defining a route, watching cargo move, earning money, and expanding the network must already feel like playing a real game.

---

# 2. V1 gameplay loop

The core loop is:

```text
Explore map
    ↓
Identify demand / production
    ↓
Build railway
    ↓
Build station
    ↓
Purchase locomotive
    ↓
Add wagons
    ↓
Create route
    ↓
Train loads cargo
    ↓
Train travels
    ↓
Cargo delivered
    ↓
Company receives revenue
    ↓
Operating costs are paid
    ↓
Expand network
    ↓
Repeat indefinitely
```

There is no formal endpoint.

The player may continue expanding the railroad indefinitely.

# 3. V1 gameplay content

## 3.1 Cargo types

V1 contains exactly three cargo types:

### Passengers

Produced by towns.

Destination:

Another town.

Properties:

* time-sensitive
* high revenue
* transported in passenger coaches

### Mail

Produced by towns.

Destination:

Another town.

Properties:

* moderately time-sensitive
* transported in mail cars

### Coal

Produced by coal mines.

Destination:

Power plants.

Properties:

* not strongly time-sensitive
* transported in coal hoppers

The cargo system must be generic enough that new cargo types can later be added through data rather than modifying the core transport system.

# 5. Towns

V1 towns have:

```text
id
name
population
position
passenger_generation
mail_generation
```

They do not dynamically grow yet.

A town consists visually of multiple buildings, roads and scenery, but the simulation treats the town itself as the primary economic entity.

Town buildings are primarily visual.

A station catchment may overlap a town.

Passengers and mail generated by that town become available to eligible stations inside its catchment.

Cargo must never be duplicated when multiple stations cover the same source.

The initial rule should be:

```text
source cargo
    ↓
eligible stations
    ↓
distributed between them
```

based initially on distance.

# 7. World model

The world is logically tile-based.

Canonical coordinates:

```text
Vector2i tile
```

Each terrain cell contains approximately:

```text
height
terrain_type
water
occupancy
rail_data
```

The game must not create one Godot node per terrain tile.

World state lives in compact data structures.

Suggested conceptual structure:

```text
WorldGrid
    terrain[]
    height[]
    occupancy[]
    rail[]
```

Rendering is a projection of that state.

---

# 8. World coordinate conventions

Define globally:

```text
TILE_SIZE = 1.0
HEIGHT_STEP = 0.25
```

These values are game units, not literal metres.

All assets are authored relative to this scale.

Example:

```text
small house:
~1 tile

large house:
1–2 tiles

factory:
3–6 tiles

locomotive:
~0.8–1 tile long

wagon:
~0.7 tile
```

These conventions must never be recreated independently inside asset scripts.

They live in one shared art/world configuration.

---

# 9. Terrain rendering

Terrain is technically 3D but intentionally simple.

It is a heightfield, not a voxel volume.

No caves or overhangs exist in V1.

Terrain is divided into render chunks.

Recommended initial chunk:

```text
32 × 32 tiles
```

A 256 × 256 map therefore uses:

```text
8 × 8 = 64 terrain chunks
```

Each chunk should normally correspond to one terrain mesh.

Terrain contains:

```text
grass
dirt
rock
water
```

Most terrain surfaces should use:

```text
vertex colors
```

instead of unique textures.

Terrain geometry should be regenerated only when the underlying terrain changes.

V1 does not require terraforming.

---

# 10. Water

Water is rendered as a very cheap plane or chunked surface.

V1 requires:

* simple color
* optional lightweight movement
* no reflection
* no refraction
* no simulation

Railway construction over water is invalid in V1.

Bridges are deferred.


Scenery should be grouped spatially by chunk.

Never create thousands of fully independent animated scene trees for static scenery.

# 12. Camera

The camera is one of the most important systems in the project.

Projection:

```text
Orthographic
```

Default orientation:

```text
yaw   = 45°
pitch = 35.264°
```

The pitch remains fixed in V1.

This preserves the isometric visual language.

Horizontal rotation is fully supported:

```text
yaw = 0° → 360°
```

Rotation is smooth.

There are also snap positions every:

```text
45°
```

# 13. Camera zoom

Zoom uses orthographic size.

Initial suggested range:

```text
closest: 4 tiles visible vertically
default: ~28 tiles
furthest: ~96 tiles
```

The exact values may be tuned.

The closest zoom must allow the player to clearly see:

* locomotive wheels
* windows
* connecting rods
* station details
* industrial machinery
* individual wagons
* cargo/loading areas

Zoom must be smooth and logarithmic rather than linear.

Mouse wheel zoom must preserve the world position beneath the cursor as closely as practical.

This is a key UX requirement.

The map should feel like something the player is directly manipulating rather than a camera floating independently above it.

# 16. Visual rendering philosophy

Runtime rendering should be cheap.

Prefer:

```text
geometry
vertex colors
shared materials
instancing
simple directional lighting
LOD
frustum culling
```

Avoid:

```text
large textures
4K textures
normal maps
unique materials per building
real-time GI
ray tracing
volumetrics
many dynamic lights
expensive transparency
```

# 17. Material system

Create a canonical material palette.

Example categories:

```text
grass
earth
stone
brick_red
brick_brown
roof_red
roof_dark
wood_light
wood_dark
iron
steel
glass_fake
water
company_primary
company_secondary
```

Most opaque assets should use a shared material which reads vertex color.

Transparent glass is not required.

Windows may use stylized opaque or mildly emissive colors.

Company-color sections may use a separate shared material with a runtime color parameter.

No asset should create arbitrary unique runtime materials without justification.

# 18. Lighting

V1 lighting:

```text
1 DirectionalLight3D
ambient environment
vertex-baked ambient occlusion
```

No dynamic GI.

No point lights for normal buildings.

Shadow distance should be limited.

Far scenery may disable shadows.

Ambient occlusion-style shading should preferably be baked into vertex color during asset generation.

# 20. 3D asset philosophy

Assets should resemble voxel art without necessarily being literal unit cubes.

Desired style:

```text
chunky geometry
clean silhouette
small bevels
simple cylinders
low-poly curves
limited palette
visible geometric construction
```

Avoid:

```text
photorealism
micro-detail
tiny geometry
complex textures
high-frequency surface detail
```

Detail should survive at gameplay zoom.

If it cannot be seen at closest supported gameplay zoom, it usually should not exist.

# 23. Railroad Art Python API

Agents should not normally manipulate low-level `bpy` for common operations.

Implement:

```text
art/railroad_art/
```

with reusable primitives.

Conceptual example:

```python
from railroad_art import *

train = SteamLocomotive("steam_440")

train.frame(length=0.85)
train.boiler(radius=0.14)
train.cab(width=0.24)
train.chimney(height=0.22)

train.add_driving_wheels(
    count=2,
    radius=0.11
)

train.add_leading_wheels(
    count=2,
    radius=0.06
)

train.company_color("cab")
train.animate_running()

train.export()
```

Low-level `bpy` remains allowed where the abstraction is insufficient.

The library is intended to encode conventions, not restrict creativity.

# 28. LOD

All substantial assets must support LOD.

Three conceptual levels:

```text
LOD0
close inspection

LOD1
normal gameplay

LOD2
distant overview
```

LOD0 preserves details.

LOD1 preserves major geometry.

LOD2 primarily preserves silhouette and color.

Small props may use only one or two levels.

LOD generation may begin using automatic import simplification.

Manual LOD is required when automatic simplification visibly damages the voxel silhouette.

# 30. Animation architecture

Animation is split into three categories.

## Mechanical animation

Examples:

```text
train wheels
connecting rods
industrial pumps
conveyors
cranes
doors
```

Mechanical animation is authored in Blender or procedurally described by asset metadata.

## Simulation-driven animation

Examples:

```text
wheel rotation speed
conveyor activation
loading animation state
```

Godot controls animation playback using simulation state.

## Transient effects

Examples:

```text
smoke
steam
sparks
dust
selection glow
```

These are created at runtime.

They are not baked into GLB animations.

---

# 31. Animation state contract

Runtime assets expose standardized animation states when relevant:

```text
idle
moving
working
loading
unloading
```

Assets are not required to implement every state.

Manifest example:

```json
{
  "id": "steam_440",
  "animations": {
    "idle": null,
    "moving": "Move"
  }
}
```

The runtime never hardcodes Blender action names directly.

It consumes generated metadata.

---

# 32. Train mechanical animation

Wheel animation must remain synchronized with train movement.

The preferred conceptual relationship is:

```text
wheel phase =
distance_travelled / wheel_circumference
```

This avoids visually sliding wheels.

For complex connecting rods, a repeating animation may be driven by the same normalized wheel phase.

Train animation speed therefore depends on actual movement rather than simply playing at a fixed rate.

---

# 33. Animation LOD

Animations have runtime LOD.

### Near camera

```text
full mechanical animation
smoke
steam
other visible effects
```

### Medium distance

```text
mechanical animation
reduced effect rate
```

### Far distance

```text
reduced animation update frequency
particles disabled
```

### Offscreen

```text
visual animation suspended
simulation continues
```

Simulation must never depend on animation state.

# 34. Rail network representation

Rail is stored logically separately from its mesh.

A rail cell contains connection information.

Conceptually:

```text

E
SE
S

W
```

The rail graph is generated from these connections.

All intersections in V1 are connected junctions.

Grade-separated crossings are deferred.

# 43. Train movement

Trains do not use physics simulation.

Movement is deterministic along the rail graph.

Train state:

```text
current_track
position_along_segment
speed
route
destination_stop
path
cargo
```

Pathfinding:

```text

```

No collision simulation exists in V1.

Trains may pass through each other.

Signals are deferred.

# 47. Revenue

Initial generic model:

```text
revenue =
quantity
× cargo_base_rate
× transport_distance
× delivery_quality
```

Passenger/mail delivery quality falls over time.

Coal has little or no time penalty.

Exact coefficients belong in data/configuration and will be balanced later.

Revenue enters the company ledger as an explicit transaction.

# 49. Bankruptcy behavior

There is no game-over condition.

If available cash cannot cover construction:

```text

```

Negative balances may be permitted temporarily if caused by recurring costs.

The finance UI makes the deficit obvious.

Loans and bonds are deferred.

# 117. V1 quality bar

V1 must feel like a game rather than an engine demonstration.

Before calling V1 complete:

* camera interaction feels polished
* construction previews are clear
* train movement is smooth
* close zoom looks intentional
* rotation reveals valid geometry from every side
* train mechanical animation works
* UI never obscures the map unnecessarily
* essential actions are discoverable
* errors explain themselves
* save/load is reliable
* core simulation is deterministic enough for tests
* the stress test does not reveal architectural failure
* art can be produced automatically through Blender
* art pipeline can execute multiple Blender jobs independently
* new compatible assets can be created without modifying the renderer
